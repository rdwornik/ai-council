## Question

For a single-binary CLI's config, pick one default format: TOML, YAML, or JSON.

## Round 1: Initial Responses

### Claude (claude-opus-4-8)

## Position

Use **TOML** as the single default config format for the CLI. It has the lowest failure surface at 2am and the best hand-editing ergonomics for the flat-to-moderately-nested config that CLIs actually need.

## Alternatives Considered

- **YAML** — Rejected. Its human-friendliness is a trap: significant whitespace, the Norway problem (`no`/`off`/`yes` coercing to booleans), version-dependent parsing (1.1 vs 1.2), and multiple ways to express the same structure. Every one of these is a support ticket that reproduces only on the user's machine.
- **JSON** — Rejected as the *default*. No comments (fatal for config a human maintains), trailing-comma intolerance, and mandatory quoting/bracing make it noisy to hand-edit. It is an excellent *machine* format, but a default config file is a human-authored artifact first.

## Decision Criteria

1. **Hand-editability** — the default config is edited by humans in a text editor, not generated.
2. **Failure mode legibility** — when parsing fails, does the error point at the actual line, and is the mistake something a tired human would make?
3. **Ambiguity / type coercion surprises** — same file must mean the same thing on every machine and library version.
4. **Comment support** — config needs inline documentation and toggle-by-commenting.
5. **Ecosystem/library maturity** in the CLI's implementation language.

## Assumptions

- Config is predominantly key–value with shallow nesting (typical CLI: flags, paths, a few sections), not deeply nested object graphs.
- The config file is authored and maintained by humans, not primarily emitted by another program.
- A mature TOML parser exists for your implementation language (true for Go, Rust, Python, Node, etc.).

## Recommendation

- **Now:** Ship TOML as the sole default. Provide a well-commented starter config generated by `cli config init`. Validate on load and emit errors as `file:line: <what and how to fix>`.
- **Don't do now:** Don't support multiple config formats "to be safe." Multi-format support triples your parse/error/test matrix and creates ambiguity about which file wins.
- **Defer:** Accepting config from stdin or a `--config-json` flag for programmatic/CI callers, *if* demand appears. That's a machine-interface concern, orthogonal to the default file format.

## Rationale

- TOML's flat-section model (`[section]`) maps directly to how CLI config is mentally organized, keeping nesting shallow where TOML is strongest — no whitespace-sensitivity, so copy-paste and indentation mistakes can't silently change meaning.
- The **Norway problem alone** justifies rejecting YAML: a user writing `region = no` gets a string in TOML and `false` in YAML. That class of bug costs hours to diagnose because the file *looks* correct.
- TOML **requires quoting on strings and has explicit typing**, so `port = 8080` is unambiguously an int and `port = "8080"` a string — the on-call engineer never guesses what the parser inferred.
- Comments (`#`) let you ship a self-documenting default and let users disable options by commenting rather than deleting — reducing "how do I turn this off" tickets.
- Single format = one parser, one error path, one set of docs — roughly a **3x reduction** in config-related test and support surface versus multi-format.

## Trade-offs

- You give up YAML's terseness for **deeply nested** structures; TOML's nested-table syntax (`[[a.b.c]]`) gets clumsy past ~3 levels. Acceptable given the shallow-config assumption.
- You give up JSON's zero-friction machine generation as the default. Mitigated by offering a JSON *input* path later if needed.
- Slightly smaller mindshare than YAML among ops folks who live in Kubernetes — a familiarity cost, not a correctness one.

## Risks

- **Config grows deeply nested over time** (likelihood: medium; impact: medium). TOML gets ugly. Mitigate by treating deep nesting as a design smell — push complexity into referenced files or subcommands rather than one giant config.
- **Chosen language's TOML library is immature or lags the spec** (likelihood: low; impact: high). Mitigate by vetting the parser before commit; pin to a spec version (TOML 1.0.0) and test round-tripping.
- **Users expect YAML because "everything uses YAML"** (likelihood: medium; impact: low). Mitigate with a clear error when a `.yaml` file is found: "This tool uses TOML; run `cli config init`."

## Signals to Revisit

- Config regularly exceeds ~3 levels of nesting or becomes list-of-objects heavy → reconsider YAML or a structured schema.
- The dominant consumer becomes machines/CI generating config programmatically → promote JSON to a first-class input.
- Your language's TOML ecosystem stalls or the maintained parser is abandoned → reassess against the best-maintained alternative.


### Openai (gpt-5.6-terra)

## Position

Choose TOML as the default config format. It is human-editable without YAML’s ambiguity and supports comments unlike JSON.

## Alternatives Considered

- YAML — rejected because its flexible syntax creates avoidable parsing and type-coercion surprises in a CLI config.
- JSON — rejected because comments are absent and hand-editing structured configuration is unnecessarily cumbersome.

## Decision Criteria

- A small team must be able to implement, document, and support it reliably.
- Users should be able to edit configuration safely by hand.
- The format needs clear, predictable typing and nesting.
- The parser and error messages should fit cleanly in one binary.
- Configuration should remain maintainable as options grow.

## Assumptions

- The config is primarily written and maintained by humans.
- Comments for explaining non-obvious settings are valuable.
- The configuration is conventional application settings, not arbitrary deeply nested documents.
- The CLI’s implementation language has a mature TOML parser.

## Recommendation

Use TOML for the default config file, such as `config.toml`.

Do now: define a small versioned schema, provide a generated/example TOML file, validate unknown keys and types with actionable errors, and document precedence between flags, environment variables, and config.

Do not do now: support multiple writable config formats or build a custom configuration language.

Defer until later: optional JSON import/export only if automation users demonstrate a real need.

## Rationale

- TOML’s comments let users retain operational context beside settings, reducing support burden.
- Its explicit tables and arrays are readable for typical CLI needs—profiles, endpoints, credentials references, and feature flags.
- YAML’s implicit booleans, dates, indentation sensitivity, and broad feature set create disproportionately costly edge cases.
- JSON is excellent for machine exchange but poor as a primary hand-authored configuration format because it cannot carry comments.
- A single supported format keeps documentation, examples, test fixtures, and bug reproduction aligned.

## Trade-offs

- TOML is less suitable than YAML for highly recursive or document-like data structures.
- Automation that already emits JSON needs a conversion step, typically a few lines or a standard library call.
- Users familiar only with YAML may face a small learning curve.

## Risks

- **Config becomes deeply nested or dynamically shaped** — likelihood: low; impact: medium. Mitigate by keeping config declarative and moving complex payloads to explicit input files or command arguments.
- **Parser behavior differs across language libraries** — likelihood: low; impact: medium. Pin a mature parser and test representative valid and invalid configs.
- **Users request YAML compatibility** — likelihood: medium; impact: low. Treat requests as evidence to assess, rather than adding dual-format support preemptively.

## Signals to Revisit

- Config schemas require frequent arbitrary nesting, heterogeneous lists, or multi-document input.
- A meaningful share of users need machine-generated config and JSON import/export becomes a recurring support issue.
- The chosen implementation environment lacks a well-maintained TOML parser with useful diagnostics.


## Round 2: Critique

### Claude (claude-opus-4-8)

Both proposals land on TOML, and both are largely right. My job here is not to manufacture disagreement — it's to find where the reasoning is thinner than the conclusion, and to say plainly whether I'm convinced. I am. But the *reasons* the two proposals give are not equally load-bearing, and both leave gaps an on-call engineer will trip over.

---

## Proposal A

**Steelman:** If the config is conventional application settings (profiles, endpoints, credential references, feature flags), authored by humans, in a language with a mature TOML parser — then TOML is exactly right. Its explicit typing and comment support cover the two things that actually generate config tickets: "what did the parser think I meant?" and "what does this setting do?" The "define a versioned schema, validate unknown keys, document precedence" action list is the strongest part of the whole council — it recognizes that *format choice is the small decision* and *validation + precedence is the big one*.

**Assessment: Agree** with the Position, **partially agree** with the emphasis. The recommendation is correct but the proposal treats format as the headline when the schema/precedence work it buries under "Do now" matters more.

**Strongest point:** "A single supported format keeps documentation, examples, test fixtures, and bug reproduction aligned." This is the real operability argument — one format means one reproduction path at 2am, not a matrix.

**Weakest assumption:** "The configuration is conventional application settings, not arbitrary deeply nested documents." This is asserted, not enforced. Config *drifts* toward nesting over three years — someone adds a list of route rules, then per-rule overrides. If that happens, TOML's `[[a.b.c]]` syntax degrades exactly when the config is most complex and most needs to be legible. A stated assumption about human intent is not a constraint on future maintainers.

**Hidden assumptions:**
1. That the flag/env/config precedence order is *discoverable* — it names documenting precedence but assumes users will read the doc. At 2am nobody reads the doc; they need `cli config resolve` to show the effective value and its source.
2. That "actionable errors" are achievable from the chosen parser. Error quality is a *parser* property, not a *format* property. Many TOML libraries emit "expected `=` at line 4" — technically true, useless to a tired human. A never checks whether the mature parser it assumes actually produces good diagnostics.

**Overlooked risks:** No mention of the **encoding/BOM/CRLF** failure mode — a Windows user saving `config.toml` as UTF-16 or with a BOM, which several TOML parsers reject cryptically. No plan for **config migration** when the versioned schema changes — it introduces a version field but never says what happens to a v1 file when the binary is v2.

---

## Proposal B

**Steelman:** If the dominant failure mode you're optimizing against is *silent misinterpretation* — a file that looks correct and parses successfully but means something the user didn't intend — then TOML is uniquely right, and YAML is uniquely dangerous. The Norway problem (`region = no` → string in TOML, `false` in YAML) is the canonical 2am bug: no error, no stack trace, just wrong behavior on one user's machine. B is the only proposal that names the *class* of failure that makes format choice a correctness issue rather than an ergonomics preference.

**Assessment: Agree**, and this is the stronger of the two proposals because it reasons from failure modes, not preferences.

**Strongest point:** "significant whitespace... copy-paste and indentation mistakes can't silently change meaning." Whitespace-sensitivity is the failure mode that reproduces *only on the user's machine* and can't be diagnosed from a screenshot — because you can't see the difference between tabs and spaces. That's the purest form of the 2am test, and B nails it.

**Weakest assumption:** "The config file is authored and maintained by humans, not primarily emitted by another program." For a *single-binary CLI*, this is the assumption most likely to invert. Single-binary CLIs get dropped into CI pipelines, Dockerfiles, and Terraform, where config is templated by a machine. B does defer a `--config-json` path, but treats machine-generation as an edge case when for a CLI it's often the *primary* deployment mode within 18 months.

**Hidden assumptions:**
1. That the `.yaml`-detection error ("This tool uses TOML; run `cli config init`") is even reachable — it assumes you can cheaply detect a YAML file, but a `.txt` or extensionless config that happens to be YAML-shaped will hit the TOML parser and produce a *worse* error than if you'd never tried to be helpful.
2. That "3x reduction in test/support surface" is attributable to format singularity. It isn't — most config support burden is *schema* churn (new keys, changed defaults), which a single format doesn't reduce at all. The 3x figure conflates format count with total config complexity.

**Overlooked risks:** Same encoding/BOM gap as A — and B's whitespace argument makes this sharper, because a user "fixing indentation" in a TOML file with an editor that reformats can introduce nothing at all (TOML doesn't care), which is fine — but B never says the *reverse* migration risk: users coming *from* YAML will indent TOML tables out of habit and be confused when it's ignored. Also unaddressed: **secrets in config**. Both A and B mention "credentials references" in passing but neither says the config format should *not* hold secrets — an operability landmine when configs get committed or logged.

---

## Revised Recommendation

**TOML. I hold the position — and B's reasoning, not A's, is why.**

The proposals didn't change my choice; they sharpened the *justification*. Coming in, I'd have defended TOML on ergonomics. B correctly reframes it as a **correctness** decision: the disqualifier for YAML is not that it's ugly, it's that it can parse successfully and mean the wrong thing with no error — the single worst property a config format can have for an on-call engineer, because it converts a config bug into a *behavior* bug with no breadcrumb. That is the argument that moved my confidence from "preference" to "position."

Where I diverge from both: **format is the 20% of this decision, and both proposals spend 80% of their words on it.** The parts that determine whether this is maintainable in three years are the parts both bury:

1. **Effective-config introspection.** Ship `cli config resolve --show-origin` that prints every effective value and whether it came from flag, env, or file. Precedence you can only *read about* is precedence you'll debug at 2am. Neither proposal makes this first-class; it matters more than the format.

2. **Error quality is a parser property, not a format win.** "Use TOML" does not get you good errors for free. Vet the specific library's diagnostics *before* committing — reject any parser whose errors don't name the line and the fix. A assumes this; B asserts it; neither verifies it.

3. **Schema versioning + migration, not just a version field.** A adds a version field and stops. Define what the binary does with a config one version behind: auto-migrate-and-warn, or refuse-with-instructions. Pick one now, because retrofitting migration onto a shipped format is where the real three-year pain lives.

4. **Encoding discipline.** State UTF-8, no BOM, LF-or-CRLF-tolerant explicitly and test it — this is the Windows-specific landmine neither proposal saw, and it's the one *I* will actually hit given my environment.

**One place I'll push back on both harder than they pushed on themselves:** the "deep nesting is a design smell, push it to referenced files" mitigation. That's true, but it silently trades a nesting problem for a *file-resolution and precedence* problem — now you have config that includes config, and the on-call engineer has to trace an include graph. If you adopt TOML, commit to keeping the config *single-file and shallow* as a hard product constraint, not a hope. The moment you reach for `include =`, TOML stopped being the right call and you should have known it two releases earlier.

**Maintain TOML as the sole default format.** Neither proposal changes the decision; both reinforce the key product constraint: a single-binary CLI operated by a realistically sized team should minimize configuration ambiguity and support surface.

Ship:

- Strict validation: unknown keys fail, types fail, errors include file and line where the parser permits it.
- Explicit precedence: flags > environment > config > defaults.
- Examples that use credential references, never secrets.
- A deliberately shallow config model; move complex structured inputs to dedicated files or subcommands.

## Synthesis (by gemini, non-participant)

## Consensus
All participants unanimously selected **TOML** as the default configuration format. This consensus was driven by strong shared evidence regarding the operational risks of YAML (ambiguous type coercion, significant whitespace) and the human-ergonomic failings of JSON (no support for comments). There was also absolute agreement that the CLI should initially support only a single format to minimize the parsing, testing, and support matrix. Both sides agreed that strict schema validation (failing on unknown keys or type mismatches) is as critical as the format choice itself.

## Unresolved Disagreements
Because the participants ultimately agreed on the outcome, the only meaningful disagreement centered on the precise nature of YAML's technical flaws.
- **The crux:** Claude argued that YAML is inherently dangerous due to silent misinterpretation (the "Norway problem" where `region = no` coerces to a boolean). Terra countered that this is overstated, as modern YAML 1.2 parsers do not coerce `no`/`off` to booleans, making the issue one of library fragmentation rather than a flaw in the YAML spec itself.
- **Stronger argument:** Claude's argument is stronger in practice. While Terra is technically correct about the YAML 1.2 specification, an on-call engineer cannot guarantee which YAML parser version a system or user is running. The operational reality of silent misinterpretation remains a massive support liability. 

## Argument Quality Assessment
Both models presented highly rigorous arguments, but Claude's Round 2 analysis elevated the debate by reframing the choice from "ergonomic preferences" to "correctness and failure modes."
- **Strongest argument:** Claude's observation that YAML's whitespace sensitivity creates a failure mode that *reproduces only on the user's machine* and cannot be debugged via a screenshot (because tabs and spaces look identical). This perfectly articulates why YAML is an operational liability for a CLI.
- **Weakest argument/assumption:** The shared assumption in Round 1 that "configuration is conventional application settings... not arbitrary deeply nested documents." As Claude later admitted in Round 2, this is merely an assertion of hope. Configuration inevitably drifts toward complexity over time, and assuming it will stay flat allows participants to wave away TOML's primary weakness (poor ergonomics for deep nesting).

## Blind Spots
While Round 2 successfully identified many Round 1 blind spots (secrets handling, BOM/CRLF encoding, parser error quality), the debate missed a few critical systemic factors:
- **Ecosystem Tooling Compatibility:** While `jq` and `yq` are ubiquitous in shell environments and CI/CD pipelines for manipulating JSON and YAML, equivalent tools for TOML (`tomlq`, `taplo`) are rarely pre-installed. This makes ad-hoc shell scripting against the CLI's config significantly harder.
- **Environment Variable Mapping:** The debate heavily emphasized precedence (Flags > Env > Config), but ignored the complexity of mapping environment variable names to nested TOML tables (e.g., how does `DATABASE_PORT=5432` map to `[database] port = 5432`?).
- **Programmatic Mutation:** Terra briefly touched on "read, modify, and write" flows, but neither participant fully addressed how difficult it is for machines to programmatically patch a TOML file while preserving user comments and formatting.

## Recommended Decision
Adopt **TOML** as the sole default configuration format for the single-binary CLI.

**Rationale:** 
A CLI's default configuration file is a human-authored artifact first. TOML provides the necessary affordances for humans (comments, obvious string quoting) without the silent misinterpretation risks of YAML (whitespace sensitivity, unpredictable type coercion). JSON is rejected as a default due to the absence of comments, which are essential for self-documenting configuration.

While TOML degrades ergonomically if the config becomes deeply nested, this limitation actually serves as a healthy forcing function to keep the CLI's configuration surface shallow and declarative. We explicitly reject the preemptive inclusion of dual-format support (e.g., allowing YAML or JSON fallbacks). The operational cost of managing a matrix of parsers, documentation, and error paths vastly outweighs the theoretical convenience for machine consumers. 

## Risks
- **Nesting Complexity:** As features grow, the config schema may drift into deep nesting where TOML's `[table]` and `[[array_of_tables]]` syntax becomes highly illegible.
- **Parser Edge Cases (Encoding):** Windows users saving configs with a Byte Order Mark (BOM) or in UTF-16, which many TOML parsers fail to handle gracefully.
- **Machine Generation Friction:** CI/CD systems or configuration management tools (like Terraform) may find templating TOML slightly more tedious than emitting raw JSON.

## Action Items
1. **Parser Selection & Vetting:** Integrate a mature, TOML 1.0.0-compliant parser. Explicitly verify that it outputs actionable errors (file, line number, and expected token) and rejects UTF-16/BOM cleanly. 
2. **Strict Schema Validation:** Implement strict parsing that immediately fails on unknown keys and type mismatches.
3. **Precedence Transparency:** Build a `cli config resolve --show-origin` command that outputs the effective configuration and explicitly states whether each value was sourced from a flag, an environment variable, the TOML file, or a default.
4. **Scaffolding Tooling:** Implement a `cli config init` command that generates a versioned, heavily commented starter `config.toml`. Ensure examples utilize credential/environment references rather than raw secrets.
5. **Migration Policy:** Define a strict versioning field in the schema (e.g., `version = 1`) and decide programmatically how the CLI handles out-of-date configs before shipping v1.
