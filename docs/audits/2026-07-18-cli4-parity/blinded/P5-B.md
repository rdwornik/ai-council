## Question

For a single-binary CLI's config, pick one default format: TOML, YAML, or JSON.

## Round 1: Initial Responses

### Claude (claude-opus-4-8)

## Position

Use TOML as the default config format. It offers the lowest 2am cognitive load for hand-edited config: explicit typing, no significant whitespace, and no footgun edge cases.

## Alternatives Considered

**YAML** — Rejected. YAML's failure modes are silent and semantic, not syntactic. The Norway problem (`no` → `false`), version strings coerced to floats (`1.10` → `1.1`), and indentation ambiguity produce configs that parse successfully but mean the wrong thing. For an on-call engineer editing config under pressure, a format that accepts your input and silently changes its meaning is the worst possible property. YAML also invites feature creep (anchors, aliases, multi-doc) that expands the maintenance surface.

**JSON** — Rejected as the *default* (though a strong runner-up). JSON has no comments, which is a real operability cost: config files can't carry the "why" inline, and operators can't disable a block by commenting it out. Trailing-comma and quote-everything rigidity make hand-editing error-prone. JSON is excellent as a *machine* format but hostile as a *human-authored* one.

## Decision Criteria

1. **Hand-editability under stress** — config is edited by humans, often during incidents. Syntax errors should be loud, immediate, and localized.
2. **Absence of silent semantic footguns** — the format must not coerce types in surprising ways.
3. **Comment support** — operators need inline rationale and the ability to toggle sections.
4. **Parser/spec stability and single-binary footprint** — must have a well-maintained, dependency-light library in the implementation language.
5. **Diff/review friendliness** — config lives in version control; line-oriented diffs matter.

## Assumptions

1. **Config is primarily hand-authored and human-reviewed**, not generated by another program. (If it were machine-generated, JSON wins.)
2. **Config is mostly flat-to-moderately-nested** (key-value with a few sections), which is the common CLI case. Deeply nested trees weaken TOML's ergonomics.
3. **The implementation language has a mature TOML parser** (true for Go, Rust, Python, JS — the usual CLI languages).

## Recommendation

**Do now:**
- Ship TOML as the sole default format.
- Fail loud on parse errors with file path, line, and column. This is 80% of the operability payoff regardless of format.
- Ship a `--print-config` / `config validate` subcommand that dumps the effective, fully-resolved config so the 2am engineer can confirm what the binary actually loaded.
- Document a canonical example config with comments, checked into the repo.

**Do not do now:**
- Do not support multiple config formats. Multi-format support triples the parsing/precedence surface and creates "which file won?" ambiguity — a classic 2am timesink.
- Do not build config inheritance, includes, or templating. That's a maintenance liability disguised as flexibility.

**Defer:**
- Adding JSON *input* support — reconsider only if a concrete machine-generation use case appears (see Signals).
- Environment-variable overrides and layered config — add later with an explicit, documented precedence order if demand is real.

## Rationale

- **TOML's failure mode is syntactic, not semantic.** A malformed TOML file won't parse and tells you where; a malformed-but-valid YAML file runs with the wrong meaning. That difference is the entire ballgame for on-call.
- **Comments are non-negotiable for operability.** The single most common config-editing action during an incident is "disable this / annotate why." JSON can't do it; TOML and YAML can. TOML wins the tiebreak on footguns.
- **No significant whitespace** eliminates an entire class of paste-and-indent errors that plague YAML edits over SSH.
- **Explicit typing with obvious literals** — strings are quoted, numbers aren't, booleans are `true`/`false` — means what you read is what you get. Roughly eliminates the type-coercion incident category (small frequency, but high blast radius).
- **Single-format = single mental model.** One parser, one precedence story, one set of docs. Cognitive load stays bounded as the tool ages.

## Trade-offs

- **Deeply nested config is uglier in TOML** than in YAML/JSON — arrays of tables (`[[section]]`) get verbose past 2-3 levels. If your config grows into deep trees, you pay ~20-30% more verbosity and reader effort. This is the main thing you give up.
- **Slightly smaller ecosystem than JSON/YAML** — fewer online snippets, some engineers less familiar with it. Mitigated by TOML's near-INI readability (most people intuit it without docs).
- **Not the native format for programmatic emission** — if you later need machines to write config, you'll add a converter or accept JSON input.

## Risks

- **Config grows deeply nested over time** (likelihood: medium; impact: medium). TOML becomes awkward. Mitigate by keeping config flat by design and pushing complex structure into separate mechanisms; revisit format if nesting depth exceeds ~3 consistently.
- **A machine-generation use case emerges** (likelihood: medium; impact: low). Mitigate by adding JSON as an *additional accepted input* — JSON is a subset-ish fit and easy to bolt on without disrupting the human path.
- **TOML unfamiliarity causes minor authoring friction** (likelihood: high; impact: low). Mitigate with a well-commented example config and a `config validate` command. Low impact because TOML is self-explanatory to anyone who's seen an INI file.

## Signals to Revisit

- **Config nesting regularly exceeds 3 levels** or requires arrays-of-objects-of-arrays → reconsider JSON (with a JSON-schema for validation) or a redesign of the config shape.
- **A real machine-generation/templating workflow appears** (e.g., config produced by orchestration tooling) → add JSON as a second accepted input format, keeping TOML as the hand-authored default.
- **Incident postmortems show config-syntax errors as a recurring root cause** despite loud parse errors → the problem isn't the format; invest in schema validation and effective-config tooling before changing formats.


### Openai (gpt-5.6-terra)

## Position
Choose **TOML** as the default configuration format. It is readable for humans, deterministic enough for reliable tooling, and substantially less error-prone operationally than YAML.

## Alternatives Considered
1. **YAML** — Rejected because its whitespace sensitivity, implicit typing, anchors, and multiple valid syntaxes create disproportionate support and debugging cost for a CLI configuration surface.
2. **JSON** — Rejected as the default because comments are unavailable and common hand-editing tasks—especially nested configuration and multiline values—are unnecessarily unpleasant. It remains valuable for machine-generated config or API interchange.

## Decision Criteria
- A typical CLI user must be able to read and edit config without specialized tooling.
- The team must be able to implement, validate, document, and support parsing with minimal ambiguity.
- Configuration errors must produce actionable diagnostics rather than surprising runtime behavior.
- The format must support common CLI needs: strings, lists, tables/objects, booleans, numbers, paths, and nested settings.
- The default should avoid creating a long-term compatibility and support burden for a single-binary product.

## Assumptions
- The config is primarily human-authored and checked into repositories or edited locally.
- The CLI needs hierarchical settings beyond a flat `.env`-style file.
- The configuration does not require advanced YAML-specific capabilities such as anchors, merge keys, custom tags, or complex document streams.
- The implementation language has a mature TOML parser with source-location-aware errors or can reasonably wrap one.

## Recommendation
**What to do now**
- Use TOML for the default config file, for example `tool.toml` or `.tool.toml`.
- Publish a small, stable schema with explicit examples for the most common workflows.
- Validate strictly at startup: reject unknown keys by default where practical, identify the offending key and file location, and explain the expected type/value.
- Support environment-variable and command-line overrides using a documented precedence order, such as: CLI flags > environment > TOML file > built-in defaults.
- Make generated starter config minimal; do not emit every possible setting.

**What not to do now**
- Do not support YAML, JSON, and TOML simultaneously at launch. Multiple formats multiply documentation, test matrices, precedence edge cases, and user-support burden.
- Do not invent interpolation, templating, includes, arbitrary expressions, or plugin-defined config syntax in v1.
- Do not silently coerce types such as `"false"` into `false` or `"30"` into `30`.

**What to defer until later**
- Add JSON import/export only if machine-generated configuration becomes a demonstrated use case.
- Add config-file includes or profile composition only after users show a recurring multi-environment configuration problem that environment overrides cannot solve.
- Consider YAML only for interoperability with an established ecosystem that already requires YAML.

## Rationale
- TOML supports the configuration structures a CLI normally needs while keeping syntax visually predictable: `[server]`, `[[targets]]`, lists, strings, booleans, and numbers cover most cases without YAML’s parsing surprises.
- YAML’s operational cost is materially higher: a single indentation mistake, unquoted scalar, or parser-version difference can turn a simple configuration issue into a support incident. This matters more than YAML’s slightly friendlier appearance.
- JSON is easy to parse but costly for humans to maintain. The absence of standard comments commonly leads users to create undocumented external notes or duplicate configuration files.
- Supporting one format instead of three avoids roughly tripling fixture coverage: parsing, validation errors, documentation examples, migration behavior, and bug reproduction all become format-specific.
- TOML’s explicitness makes a strict schema practical. For a CLI with perhaps 20–100 settings, clear validation and deterministic precedence deliver more user value than a maximally flexible syntax.

## Trade-offs
- TOML is less familiar than JSON and less ubiquitous than YAML in infrastructure ecosystems.
- Deeply nested structures can become verbose, particularly when arrays of tables are involved.
- Users cannot use YAML anchors/merge keys to reduce duplication; repeated values must instead be handled through environment overrides, shell tooling, or later composition features.
- Some ecosystem integrations may require a conversion step, though this is typically a small one-time cost compared with permanently supporting multiple native formats.

## Risks
- **Users expect YAML because adjacent tooling uses it.** Likelihood: medium; impact: low to medium.  
  Mitigate with clear examples, a concise migration/import guide, and an optional `tool config validate` command that gives excellent errors.

- **The initial TOML schema becomes difficult to evolve.** Likelihood: medium; impact: medium.  
  Mitigate by versioning only when needed, reserving a top-level metadata section if appropriate, accepting omitted fields with defaults, and avoiding renaming keys without a compatibility period.

- **Configuration needs grow into environment-specific composition.** Likelihood: medium; impact: medium.  
  Mitigate initially through explicit environment variables and flag overrides; add profiles or includes only after observing repeated, concrete demand.

- **Parser diagnostics are insufficient for supportability.** Likelihood: low to medium; impact: medium.  
  Mitigate by selecting a maintained TOML library that reports line and column information, then layer semantic validation errors with full key paths such as `targets[2].timeout`.

## Signals to Revisit
- More than approximately 20% of support requests or onboarding failures concern TOML syntax or structure.
- A major target ecosystem requires users to maintain the same configuration in YAML-native systems and conversion becomes a recurring source of errors.
- At least several independent users need shared fragments, inheritance, or multi-environment composition that cannot be cleanly handled through environment variables and CLI overrides.
- The config becomes primarily machine-generated or exchanged over APIs; in that case, add JSON import/export or reconsider JSON as an additional supported interchange format, not necessarily the human default.


## Round 2: Critique

### Claude (claude-opus-4-8)

Both proposals reach the same conclusion I would (TOML), so my job here is to interrogate the reasoning quality, not just the answer. Two proposals arriving at the same destination via slightly different routes is a chance to catch shared blind spots.

## Proposal A

**Steelman first:**
For this proposal to be exactly right, the config must be primarily hand-authored, flat-to-moderately-nested, edited under stress, and reviewed in version control. Under those conditions, TOML's syntactic-not-semantic failure mode is decisive: a wrong TOML file won't run, a wrong YAML file will run wrong. The proposal's real thesis — "a format that accepts your input and silently changes its meaning is the worst possible property for on-call" — is the single most important sentence anyone has written in this council. If that framing holds, TOML wins on the criterion that matters most at 2am.

**Your assessment: Agree** with the Position. The reasoning is operability-first and correctly identifies that the format debate is secondary to loud parse errors and effective-config tooling. The "Do now / Do not / Defer" split is exactly the discipline I want. It resists multi-format support and templating, which are the real 2am traps.

**Strongest point:**
The distinction between syntactic and semantic failure. This is the whole ballgame and the proposal names it explicitly. A malformed config that *fails* is a good config file compared to a malformed config that *runs*.

**Weakest assumption:**
Assumption 2 — "config is mostly flat-to-moderately-nested." This is asserted, not derived. If the config grows deep (arrays of tables of arrays), TOML's `[[section]]` ergonomics degrade sharply, and the proposal's own trade-off section admits a 20-30% verbosity tax. What breaks: the 2am engineer now stares at deeply-indented `[[servers.pools.endpoints]]` blocks and *cannot tell where they are in the tree* — which is exactly the paste-and-indent confusion the proposal claims TOML avoids. TOML's readability advantage is real only at shallow depth. It does not degrade gracefully.

**Hidden assumptions:**
1. That the engineer editing at 2am *has the schema in their head or in front of them*. Every claim about "loud parse errors" covers syntax, but a syntactically valid TOML file with a misspelled key (`tiemout = 30`) parses fine and silently uses the default. This is TOML's own silent-semantic footgun, and the proposal — while criticizing YAML's silent failures — never acknowledges TOML has one too. Reject-unknown-keys (which Proposal B explicitly recommends) is what closes this gap, and A omits it.
2. That "near-INI readability" means engineers intuit TOML correctly. INI familiarity actively *misleads*: people assume INI's untyped, quote-optional, dialect-varying rules, and TOML is stricter. Familiarity-that-is-subtly-wrong is worse than unfamiliarity.

**Overlooked risks:**
- Silent key-typo failures (above) — the most common real-world config bug, and unaddressed.
- The `--print-config` output format is unspecified. If it dumps TOML, great; if it dumps a Go struct or JSON, the engineer now reconciles two representations at 2am. The tool is proposed but its contract isn't.

## Proposal B

**Steelman first:**
For this to be exactly right, the same hand-authored assumptions hold, *plus* the recognition that format choice is necessary but insufficient — the operability win comes from **strict schema validation, unknown-key rejection, and a documented precedence order (CLI > env > file > defaults)**. B's thesis is that TOML makes strict validation *practical*, and validation is what actually protects the 2am engineer. If the team will invest in schema + validation, B is right.

**Your assessment: Agree** with the Position, and I rate B's *reasoning* slightly higher than A's on the point that matters most: B explicitly recommends rejecting unknown keys and reporting full key paths (`targets[2].timeout`). That directly closes the silent-typo hole A left open. B understood that the format is a substrate for validation, not the safety mechanism itself.

**Strongest point:**
"Reject unknown keys by default where practical, identify the offending key and file location, and explain the expected type/value." This is the actual operability payload. It converts a class of silent 2am failures into loud startup failures. This is what I want on the runbook.

**Weakest assumption:**
"Reject unknown keys by default where practical." The phrase "where practical" is doing enormous load-bearing work and hides a genuine conflict: strict unknown-key rejection fights forward/backward compatibility. When you add a v2 key and an operator running v1 binary hits it — or vice versa — strict rejection turns a benign extra key into a hard startup failure. What breaks: rolling upgrades and mixed-version fleets. The proposal names schema evolution as a *separate* risk but never notices it collides head-on with its own strict-rejection recommendation. You cannot maximize both.

**Hidden assumptions:**
1. That a "small, stable schema" and "reject unknown keys" coexist peacefully with "versioning only when needed." These pull in opposite directions. Strict validation makes schema evolution *harder*, not easier, and B treats them as independent lines in the recommendation.
2. That environment-variable overrides are a clean substitute for the composition/inheritance features it defers. Env overrides are string-typed and flat; they map badly onto nested TOML tables. B leans on env-overrides to avoid building includes, without noticing env vars can't cleanly address `targets[2].timeout` — the very key-path structure B is proud of validating.

**Overlooked risks:**
- The strict-rejection / version-skew collision, above. This is a real 2am scenario: operator upgrades the binary, config now has a key the new binary considers valid but an unrelated node running the old binary rejects. Fleet split-brain.
- Env-override precedence with typed values: `TOOL_TIMEOUT=30` — is that the string `"30"` or int `30`? B forbids coercion in the file but says nothing about how the env layer types its values, which is where coercion sneaks back in.

## Where both proposals share a blind spot

Both treat "TOML fails loud" as covering the failure surface. Neither fully reckons with the fact that **TOML's silent failure is the misspelled/wrong-type-but-valid key**, and only B partially addresses it (with a recommendation that then conflicts with schema evolution). The format choice is nearly settled; the unsolved problem is the validation-vs-evolution tension, which neither resolves.

## My Revised Recommendation

**I maintain TOML.** Nothing here moved me off the format, because both proposals independently confirmed the core operability argument I already hold: syntactic failure beats semantic failure, and single-format beats multi-format.

**But I update my *implementation contract*, and I credit Proposal B for the change.** B's insistence on unknown-key rejection with full key-path errors caused me to promote validation from "nice to have" to a mandatory launch requirement — and, more importantly, to confront the tension B left dangling. My revised position:

1. **TOML, single format, fail loud on syntax** — with file/line/column. (Both proposals; settled.)

2. **Validate the schema at startup with full key-path errors** (`targets[2].timeout: expected integer, got string`). Adopted from B. This closes the silent-typo hole A ignored.

3. **On unknown keys: warn loudly by default, do not hard-reject.** This is where I break from B and refuse to split the difference. B's "reject unknown keys where practical" trades a rare 2am failure (typo) for a more dangerous one (version-skew startup failure across a fleet). At 2am, a binary that *refuses to start because of a harmless extra key* is worse than one that starts and prints `WARNING: unknown config key 'tiemout' at line 12, ignored`. The warning gives the engineer the typo *and* keeps the service up. Hard-reject is the wrong default for a single-binary CLI that will run across mixed versions.

4. **`--print-config` must emit valid TOML**, round-trippable, showing the fully-resolved config with a provenance annotation per key (`# from: CLI flag` / `# from: env` / `# from: file` / `# from: default`). A proposed this tool but not its format; the provenance annotation is the addition that makes it actually useful during an incident — the 2am question is not "what is the value" but "*why* is it this value."

5. **Documented precedence, CLI > env > file > default**, adopted from B — with the explicit note that env overrides are string-typed and are only supported for scalar keys, never for structured/nested values. This prevents B's unstated env-coercion footgun.

**Precise statement of what changed my mind:** Proposal B's unknown-key/key-path validation recommendation. It identified the silent-failure mode that TOML shares with YAML and that Proposal A — despite building its entire case on avoiding silent failures — never noticed in its own chosen format. I adopted the validation, and rejected B's hard-reject default because it re-introduces a worse 2am failure than the one it prevents.


### Openai (gpt-5.6-terra)

## Proposal A

### Steelman first

This proposal is exactly right if the CLI’s configuration is primarily authored and edited by humans, is moderately structured rather than deeply recursive, and will be operated by people who may need to make changes quickly without a specialized editor or validation pipeline.

Under those conditions, TOML gives the best operational balance:

- It supports comments and readable grouping.
- It avoids YAML’s implicit typing and whitespace-sensitive structure.
- It is less tedious than JSON for routine hand edits.
- A single parser and schema keeps a small team’s support and test burden contained.
- The proposed effective-config and validation commands make the format choice operationally useful rather than merely aesthetic.

If the product has perhaps tens—not hundreds—of settings, few deeply nested repeated objects, and no immediate machine-generated-config requirement, TOML is the lowest-risk choice.

### Your assessment

**Agree with its Position.**

TOML is the best default among these three for a single-binary CLI when human-authored configuration is the primary use case. Proposal A correctly prioritizes failure behavior and supportability over syntax popularity.

However, I disagree with one implementation implication: it treats environment-variable overrides as something to defer categorically. The format decision does not require a broad configuration layering system, but environment-variable overrides for a small set of deployment-sensitive values—tokens, endpoints, log level, timeouts—are often a day-one operational requirement. A CLI that must work in CI, containers, and shell automation should not force secrets into a TOML file merely to preserve a minimal v1 design.

### Strongest point

**“TOML’s failure mode is syntactic, not semantic.”**

That is the strongest argument in the entire set of proposals. YAML’s worst problem is not that it is harder to parse or more feature-rich; it is that apparently reasonable human input can be accepted and interpreted differently than intended. For an operator, a loud failure is almost always cheaper than a successful parse with incorrect behavior.

### Weakest assumption

**The config will remain flat to moderately nested.**

This is plausible, but not guaranteed. CLI configuration often starts simple and then accumulates targets, rules, profiles, routing policies, credential sources, and plugin settings. Once the core model becomes “a list of objects containing lists of objects,” TOML’s arrays-of-tables syntax becomes difficult to author and review.

If this assumption fails, the result is not merely ugly config. The team may begin adding custom shorthand, profiles, includes, or separate files to compensate—creating exactly the configuration complexity the proposal seeks to avoid.

The mitigation should not be “change formats once nesting exceeds three levels.” Format migrations are expensive and politically difficult after users have config in repositories. The better mitigation is to constrain the v1 schema deliberately: avoid encoding an arbitrarily deep domain model in the main config file.

### Hidden assumptions

1. **The implementation language’s TOML ecosystem is mature enough in practice, not merely present.**  
   A parser existing is insufficient. The team needs reliable source positions, predictable decoding behavior, maintained security fixes, and a way to distinguish syntax errors from semantic schema errors.

2. **Comments are needed in the live config file rather than solved by generated examples, docs, or `config init`.**  
   This is often true, but it is assumed rather than established. Comments are a real TOML advantage, but they are not automatically decisive for every CLI—especially if the config is usually generated or managed centrally.

### Overlooked risks

- **Duplicate keys and table redefinition behavior.** TOML prevents some ambiguity, but the exact parser behavior and diagnostics around duplicate keys, dotted keys, and table ordering must be tested. “Strict TOML” does not automatically mean “clear user errors.”
- **Date/time types leaking into the product schema.** TOML has native datetime constructs. If the decoder maps these inconsistently across languages or application types, users can encounter surprising timezone and serialization behavior. The schema should explicitly define accepted timestamp representations rather than inherit parser behavior.
- **Secret handling.** A readable local TOML file encourages users to place API tokens and passwords in it. The proposal discusses operability but not the security and distribution implications of config files checked into repositories.
- **Configuration discovery ambiguity.** One format does not prevent confusion over whether the binary loaded `./tool.toml`, `~/.config/tool/config.toml`, an explicit `--config` path, or a project-level file. File discovery and precedence are often a larger support burden than the syntax itself.
- **“Comment out a block” is not consistently simple in TOML.** TOML supports comments, but commenting out multi-line structures can still be tedious and error-prone. It is better to provide an explicit `enabled = false` field where disabling a configured object is a supported operational action.

## Proposal B

### Steelman first

This proposal is exactly right if the CLI is expected to run both interactively and in automation from the beginning, and if its operators need a conventional, explicit precedence model across command-line flags, environment variables, file configuration, and defaults.

In that environment, TOML is the appropriate durable human-authored base format, while a strict schema and documented precedence model prevent operational confusion. Proposal B is especially compelling if the tool will be used in CI, containers, and team-managed repositories, where environment variables are not optional convenience features but the normal way to inject credentials and deployment-specific values.

The proposal’s restraint is also correct under this scenario: one input format, no interpolation, no includes, no expression language, no plugins defining their own syntax.

### Your assessment

**Partially agree with its Position.**

I agree that TOML should be the default format and that YAML and JSON should not be supported as equivalent first-class config formats at launch.

I only partially agree because Proposal B turns a format decision into a relatively expansive v1 configuration-system commitment:

- strict unknown-key rejection,
- complete CLI/environment/file/default precedence,
- source-location-aware semantic validation,
- possibly a reserved metadata/versioning section.

These are individually reasonable ideas, but a small team with a single-binary CLI should not automatically build all of them before proving they are needed. The practical objective is to ship a reliable config surface, not a miniature configuration framework.

In particular, “reject unknown keys by default” is not universally correct. It is right for a stable, centrally controlled schema where typos are more likely than forward compatibility needs. It can be harmful if users share config between binary versions, use staged rollouts, or have mixed-version CI and developer environments. The product must make a conscious compatibility choice rather than treating strictness as free.

### Strongest point

**Supporting multiple formats multiplies more than parser code: it multiplies documentation, fixtures, diagnostics, migrations, and support reproduction.**

This is the most pragmatic argument in Proposal B. Teams routinely underestimate the cost of “we can just accept YAML too.” The parser may be cheap; every behavior surrounding it is not. A small product team should have one canonical syntax, one canonical example, and one set of diagnostic expectations.

### Weakest assumption

**A complete environment-variable override layer is simple enough to include immediately.**

It is not automatically simple. Once environment overrides are introduced, the team must settle questions such as:

- Which keys are overrideable?
- How are nested values named?
- How are lists and maps represented?
- Are empty strings meaningful or treated as absent?
- How are values typed and validated?
- Can secrets be supplied only via environment variables?
- Does an environment value override an explicit file value even when malformed?
- How does the tool show provenance in `--print-config` without exposing secrets?

If this assumption fails, the team ships an inconsistent and undocumented override system that becomes a larger source of incidents than the config format itself.

The correct v1 compromise is not necessarily “no environment variables.” It is a deliberately narrow override set: secrets and a small number of operational knobs, each explicitly named and documented.

### Hidden assumptions

1. **The CLI has a sufficiently stable schema for strict unknown-key rejection.**  
   That assumes users will not routinely run older binaries against newer shared config files, and that future schema evolution can be handled without costly compatibility windows.

2. **Environment variables are an appropriate transport for all deployment-specific configuration.**  
   They are suitable for secrets and scalar settings, but poor for structured values, large lists, and complicated policies. The proposal assumes the config model will remain compatible with environment-variable representation.

### Overlooked risks

- **Precedence becomes invisible behavior.** Even a documented order—flags > environment > file > defaults—does not make it easy for an operator to identify which source won for each setting. A `--print-config` command should show provenance, not merely resolved values.
- **Secrets can leak through diagnostic output.** Effective-config output, debug logs, shell history, and CI metadata can expose credentials unless fields are explicitly redacted.
- **Unknown-key policy can block upgrades.** If a repo updates its config before all developer machines and CI runners update the binary, strict rejection makes otherwise harmless forward-compatible fields a hard failure.
- **Environment variables create platform and shell inconsistencies.** Case handling, quoting, newline behavior, Unicode, and maximum environment size vary. The design should avoid pretending environment variables are a general structured-config channel.
- **“Minimal starter config” can under-document dangerous defaults.** A short generated file is good, but defaults that materially affect safety, network access, destructive operations, or credential lookup must be visible somewhere authoritative.

# Revised recommendation

**Maintain TOML as the sole default configuration format.**

Neither proposal changes the core decision because both correctly identify the actual constraint: a single-binary CLI, likely maintained by a limited team, needs a configuration system that users can edit, the team can diagnose, and support can reproduce without maintaining three parallel semantics.

Choose **TOML**, not YAML and not JSON.

- **Reject YAML** because its semantic ambiguity and whitespace-sensitive structure create disproportionately expensive support incidents. YAML’s flexibility is not value for this product; it is unbounded surface area.
- **Reject JSON as the default** because configuration is a human operational interface, not just a serialization format. Lack of comments and unpleasant manual editing impose recurring friction. JSON may later be accepted as an explicitly requested machine-input format, but it should not drive the initial design.
- **Do not support more than one file format in v1.** No YAML compatibility mode, no JSON “also works,” and no auto-detection. That is not user friendliness; it is permanent test and support debt.

## What to ship now

1. **One explicit TOML config path mechanism**
   - Support `--config /path/to/file`.
   - Define at most one conventional default discovery location or a very small, documented sequence.
   - On startup or via verbose mode, show the loaded config path.

2. **A deliberately constrained TOML schema**
   - Favor shallow tables and simple lists.
   - Avoid deeply nested arrays of tables in v1.
   - Use explicit `enabled = false` fields rather than expecting operators to comment out structured blocks.
   - Do not expose TOML-specific types unless the product explicitly needs them; especially avoid accidental datetime semantics.

3. **Strict parsing and useful validation**
   - Fail on TOML syntax errors with path, line, and column.
   - Validate semantic errors with full key paths and expected types.
   - Reject unknown keys for the initial stable schema **unless** the product explicitly supports mixed binary/config versions. If mixed-version rollout is expected, define a compatibility policy before enabling strict rejection.

4. **A diagnostic command**
   - Provide `config validate`.
   - Provide `config show` or `--print-config` to display the resolved configuration.
   - Redact secrets.
   - If overrides exist, show each value’s source: default, file, environment, or flag.

5. **Narrow, explicit environment support**
   - Support environment variables for secrets and a small set of deployment-critical scalar values from day one if the CLI will run in CI or containers.
   - Do not implement generic automatic mapping from every TOML key to environment variables.
   - Document each supported variable individually.

## Explicitly do not build now

- YAML or JSON config input.
- Includes, imports, inheritance, profiles, merge behavior, or templating.
- Generic environment-variable mapping for nested structures.
- Arbitrary interpolation or expressions.
- A config versioning framework before there is an actual incompatible migration.

## Revisit only with evidence

Reconsider the format or add JSON input only if one of these occurs:

- Configuration becomes primarily machine-generated.
- The schema demonstrably requires deeply nested, repeated object structures that users struggle to express in TOML.
- A major integration requires JSON or YAML as an exchanged artifact and conversion is producing real support cost.
- Measured support data—not preference—shows TOML is a recurring source of onboarding or operational failure.

The key decision is not “which syntax is nicest.” It is to keep configuration boring enough that the actual team can ship it, validate it, explain it at 2am, and evolve it without inheriting a configuration platform they never intended to build.

## Recommended Decision
**Ship TOML as the single, default configuration format.**

**Rationale:**
Configuration is fundamentally a human-to-machine interface, often edited under stress. TOML perfectly threads the needle for this use case: it supports comments (unlike JSON) and fails loudly on syntax errors rather than silently coercing types or misinterpreting indentation (unlike YAML). 

By restricting the CLI to a single format, you bound the cognitive load for operators and the maintenance burden for your team. You trade away YAML's ubiquity and JSON's machine-native ubiquity to buy deterministic, predictable behavior at 2am. 

## Risks
- **Nesting Degradation:** TOML's readability plummets when configurations become deeply nested (e.g., arrays of tables of arrays). 
  *Mitigation:* Force a flat-to-moderately-nested domain model in your schema. If complex policies or routing rules are needed, push them into separate domain-specific files rather than the core CLI config.
- **Type Coercion via Env Vars:** Introducing environment variables can inadvertently reintroduce the type-coercion bugs TOML was chosen to avoid (e.g., is `TIMEOUT=30` a string or an int?).
  *Mitigation:* Do not blindly map env vars to the config tree. Explicitly define which scalar values can be overridden and handle their type conversion strictly in the application code.

## Action Items
1. **Implement a strict TOML parser** that fails loudly on syntax errors, reporting the exact file path, line, and column.
2. **Implement Schema Validation** that reports full key paths for type mismatches (e.g., `targets[0].timeout must be an integer`). 
3. **Warn, do not reject, on unknown keys.** Emit a loud, visible warning to catch typos without breaking rolling upgrades or shared dotfiles across different binary versions.
4. **Implement a `config validate` and `--print-config` command.** The print command must emit valid TOML, annotate the source of each value (File, Env, CLI, Default) via comments, and **redact all fields marked as secrets**.
5. **Support explicit, narrow environment variables.** Only support env vars for a predefined list of operational knobs and secrets. Establish a strict precedence: CLI Flags > Env Vars > TOML File > Built-in Defaults.
6. **Do not support YAML or JSON** as alternative config files. Defer JSON entirely unless a concrete machine-generation use case forces you to accept JSON via stdin later.
