## 0. Ground truth — what the input layer is today

Three facts anchor everything below:

1. **The GUIDE itself declares the input stage the highest-leverage point.** "Question framing is the only bias-control point with no safety net… the highest-leverage step in running a debate" (GUIDE §Neutralizing bias). The operator's claim that boosting is the CORE is not a new thesis — it is already the repo's own doctrine, in prose, with zero mechanism behind it.
2. **The only input intelligence that exists runs *after* authoring and can't reach half the modes.** `detect_mode()` classifies an already-written question, and its prompt offers **only pick/ideas/judge** (`mode_detector.py:14-22`) — `research` is structurally unreachable by auto-detection; it must be forced via `-M`/frontmatter. Its failure fallback is hardcoded `pick`, not the configured default (#64). Lane B applies no interactive confirm at all; #53's corpus incident (a directive run as `research`, failing all six framing checks) went through ungated.
3. **Everything the operator calls the core is filed and unbuilt:** #36 (authoring advisor), #37 (decomposition advisory), #38 (read-back guide) — all [S13], all P3; #9 (the `/council-question` template + question-quality gate) is explicitly DEFERRED. The CONTRACT's §8 step 2 assigns authoring to the caller "per ADR-95 lane discipline: architect frames substance; CC expands mechanically" — i.e. today's design *presumes* a competent caller-side author that the record shows does not exist (prior audit break B1).

One more constraint that shapes every design below: **ADR-95's lane discipline is in direct tension with boosting itself.** A boost that improves a weak question is *shaping substance*, which ADR-95 reserves for the architect. Any boosting mechanism needs an explicit boundary rule — the candidate offered throughout this report: **the boost may restructure, interrogate, and flag; it may never assert a fact the caller didn't give.** Whether that rule is enough to keep ADR-95 intact, or ADR-95 needs an amendment naming the boost as a sanctioned co-author, is itself a contested point (both options live).

## 1. The boosting mechanism — three architectures, held in tension

What the field does that we don't: ChatGPT's deep research inserts an **intermediate clarifier model** between the raw ask and the expensive run, while the **API deliberately skips it and tells developers to build their own rewrite/clarify step** ([OpenAI deep research guide](https://developers.openai.com/api/docs/guides/deep-research), [cookbook](https://developers.openai.com/cookbook/examples/deep_research_api/introduction_to_deep_research_api), [help center](https://help.openai.com/en/articles/10500283-deep-research-faq)) — an exact analogue of our Lane B (operator product) vs Lane A (machine API) split. Spec-driven tooling (Kiro, GitHub Spec Kit) made "formalize intent first, code/run later" the 2026 mainstream, with approval gates between intent → plan → execution ([Fowler's SDD tool review](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [Spec Kit](https://github.github.com/spec-kit/), [BCMS SDD guide](https://thebcms.com/blog/spec-driven-development)). And the elicitation literature warns that models *recognize* ambiguity but **rarely ask unprompted** ([Knowing but Not Showing](https://arxiv.org/html/2605.25284v1)) — a clarify behavior must be forced by architecture, not hoped for.

### Design A — single-shot reformulator ("the compiler")

One LLM call, template-constrained: raw ask + caller-supplied context → draft GUIDE-conformant brief, plus (a) a provenance tag per Current-State line (`given` / `restructured` / `ASSUMED — verify`), (b) a confidence note, (c) the list of holes it could not fill. The standard query-rewriting move, industrialized ([Query Optimization survey, arXiv 2412.17558](https://arxiv.org/html/2412.17558v3); [LLM-QA agents survey, arXiv 2503.19213](https://arxiv.org/html/2503.19213)); EchoPrompt-style restatement is also a cheap ambiguity-surfacing trick (same survey).
**Where it runs:** either side. Caller-side = #36 shipped as a template+prompt pack in `protocols/` (zero new surface). Council-side = a stateless `council boost --raw "..."` subcommand emitting `brief.md` (file-in/file-out, CLI-as-ABI preserved).
**Cost:** one cheap call (~$0.001–0.01, deepseek-class); latency seconds.
**Conflicts:** ADR-95 (substance-shaping — mitigated but not dissolved by the provenance rule); the known failure mode is **confabulated specificity** — the boost invents the "587 notes"-style facts the GUIDE demands, because the template rewards concreteness. Design A alone has no channel to *get* missing facts except inventing or flagging them.

### Design B — bounded clarify-loop ("the interviewer")

Detect underspecification first (CLAMBER-style ambiguity taxonomy: [arXiv 2405.12063](https://arxiv.org/pdf/2405.12063); ClarifyGPT's sampled-divergence test: [arXiv 2310.10996](https://arxiv.org/pdf/2310.10996)), ask the caller ≤N targeted questions (N≈3), then reformulate as in A. 2026 work gives principled ask/don't-ask criteria — expected value of perfect information over the missing fields ([Structured Uncertainty, OpenReview](https://openreview.net/forum?id=dc8ebScygC)), information-gain-driven clarifiers ([arXiv 2606.03135](https://arxiv.org/pdf/2606.03135)), and future-turn simulation trading informativeness against interaction cost ([ICLR 2025, arXiv 2410.13788](https://arxiv.org/html/2410.13788v2)). Requirements-engineering results are sobering and relevant: LLM interviewers reach near-human quality on explicit requirements but capture only ~70% and stay weak on *implicit* ones ([LLMREI, arXiv 2507.02564](https://arxiv.org/html/2507.02564v1); [ReqElicitGym, arXiv 2602.18306](https://arxiv.org/pdf/2602.18306)) — a clarify-loop reduces, not eliminates, the bad-boost problem, and over-clarification annoys ([Clarification Is Not Enough, arXiv 2605.25204](https://arxiv.org/pdf/2605.25204)).
**Where it runs:** caller-side is natural — the delegating agent already has an interaction channel to its human *and* repo access to answer many questions itself without bothering anyone (the cheapest clarification is self-service retrieval from the caller's own tree). Council-side, Lane A has **no ask-back channel at all** — the CLI blocks synchronously and speaks only exit codes and files; a council-side clarify-loop either becomes a two-phase file protocol (boost returns `questions.md`, caller answers, resubmits) or needs MCP elicitation (§5).
**Cost:** 2–4 calls + a human/agent round-trip; the interaction cost is the real price.
**Conflicts:** ADR-11 (if council-side and interactive); Lane B's fire-and-forget batch contract (a clarify-loop in the inbox becomes a two-pass tray — see §4); ADR-95 (less than A — asking is the architect-respecting move; the answers are genuine caller substance).

### Design C — classify-then-decompose pipeline ("the front office")

Stage 1: cheap typed classification of the raw ask — {research, decision(pick/judge), ideas, hybrid, reject-as-directive} via structured-output enum, the 2026 production standard that matches fine-tuned encoders at 5–30 intents ([Respan intent-classification guide](https://www.respan.ai/articles/intent-classification-with-llms); entry-point classifier pattern: [NVIDIA AI-Q](https://docs.nvidia.com/aiq-blueprint/2.0.0/architecture/agents/intent-classifier.html), [Hybrid AI Routers, arXiv 2504.10519](https://arxiv.org/pdf/2504.10519)). Stage 2: per-type schema fill (A, or B when holes remain). Stage 3: decomposition when compound — the field distinguishes parallel vs sequential vs no-decomposition, and warns LLM decompositions are unstable ([Reasoning in Trees, arXiv 2601.11255](https://arxiv.org/pdf/2601.11255)) — this is #37 made mechanical. Stage 4: the #9 quality gate (§3). Output: 1..N conformant briefs plus a commissioning plan (which sub-brief feeds which — see §2).
**Where it runs:** this much machinery only makes sense once — building it per-caller contradicts its point, so C gravitates council-side (or into one shared caller-side plugin, which is the same code with a different owner label).
**Cost:** 2–3 cheap calls per commission + the build (M–L). It subsumes routing (§2) and hosts the gate (#9), which is its efficiency argument — and its scope-creep argument.

**Held in tension.** A is the minimum honest mechanism and ships this week; B is what the elicitation literature says actually closes the information gap, at interaction cost; C is the only one that solves routing and decomposition in the same motion. They compose (C's stage 2 *is* A, escalating to B on holes) — but the operator should choose the **first** build deliberately, because each anchors a different owner: A anchors caller-side, B anchors an interaction channel, C anchors a council-side entry stage. The OpenAI precedent suggests a lane split is also coherent: council-side boost for Lane B (operator), published advisor prompts for Lane A (agents) — two options live there too.

## 2. Type routing and the hybrid-question problem

Today's router cannot implement the operator's design: it fires post-authoring, cannot emit `research` (§0.2), and its fallback ignores config. Whatever else is decided, routing must move **into** the boost stage — classify the *raw ask*, not the finished brief. Three live options for what it routes *to*:

- **R1 — hybrid as composition (no runtime change).** Classifier adds a `hybrid` class; the boost splits a hybrid ask into a research sub-commission ("what does the field know about the candidates?") whose output feeds a pick sub-commission ("given this evidence pack, which?"). The CONTRACT already supports sequencing — this is the prior audit's remedy (b), now with a mechanism to do the splitting instead of hoping the caller does. The GUIDE already contains the seam: research mode's `Background` section asks "what decision this will inform" — a hybrid brief is one where that line names the *next commission*. Cost: prompt+schema work only. Risk: two runs' cost and latency for the flagship question type; the caller must carry evidence between runs (the boost should emit both briefs up front, the second with an `evidence-pack: <path>` hole).
- **R2 — hybrid as a real third lane (grounded-pick).** The prior audit's Swing A seen from the input side: routing gains a first-class `grounded-pick` target where the research pool seeds an evidence pack into Round 1. Cleanest caller experience; largest conflict surface (ADR-04 mode system, ADR-05/invariant-6 research isolation, ADR-06 cost posture). The input layer should *not* drive this decision — it is a PROCESS-stage architecture bet — but the router design must leave the class representable so R2 can land later without re-teaching the classifier.
- **R3 — don't classify; make the caller declare the deliverable.** The GUIDE's own recognition test is output-based ("what should I do?" vs "what does the field know?"). Make `deliverable:` a required boosted-brief field (survey / option-set / verdict / decision), and derive mode deterministically from it — no classifier LLM, no misclassification class, #53 dies structurally. Hybrids surface honestly as "decision, but the facts are stale/unknown" — i.e. R3 still needs R1's split behind it. Weakness: pushes the judgment back onto the asker that boosting was supposed to supply; best used as the *validation* of a classifier's guess rather than the sole mechanism (both sub-options live).

**H1 sensitivity (flagged, not resolved):** if H1 resolves toward the creativity/boosting engine, the router needs an ideas-first path: the GUIDE already advises running an `ideas` round to generate the option set before a consequential `pick` — under H1-creativity, the boost should *default* to proposing that two-step plan whenever the raw ask arrives option-less, making option-set generation part of the input layer. Under H1-decision, the same case is just R1 composition with `ideas` in the first slot. Either way the mechanism is shared; only the default flips.

Production hygiene regardless of option: log the routed class on every run and evaluate per-class precision on the accumulated corpus ([Respan](https://www.respan.ai/articles/intent-classification-with-llms)) — the inbox archive is already a labeled dataset nobody is using.

## 3. Template-as-mechanism — what the 599 lines codify to

The GUIDE's content is validated by the field: the five-element research-brief shape it teaches (question+scope / background / facets / source rules / output wanted) matches 2026 deep-research prompting practice almost clause for clause ([builderlab framework](https://www.builderlab.ai/p/prompt-frameworks-for-unlocking-chatgpts), [Integral](https://www.integral.com.au/craft-the-ultimate-deep-research-prompt)). The gap is executability, and it splits cleanly:

**Deterministically codifiable (a linter, no LLM — fits the repo's validators-only Layer-2 culture):** section presence/order per mode; frontmatter keys against `council_frontmatter_keys`; headline is one sentence; 2–4 options per sub-question, 3–7 sub-questions, 4–8 constraints; 40–80-line size; research: ≤3 facets, recency window present, source-types present; banned-content list (Model/Mode/Effort tables, "Read CLAUDE.md", COMMIT-marker steps — GUIDE §What-NOT); escape option present ("a different approach — name it"); *measurable* bias proxies — option-description length parity (anchoring), first-person leaning markers ("I think", "obviously", "ideally"). Cheap, fail-fast, testable — `scripts/validate_brief.py` in the existing idiom.

**LLM-judgment required (the #9 gate proper):** leading-headline detection (problem vs pre-chosen answer); asker-leakage beyond the regex-able markers; "could a reasonable person draw a different conclusion from this Context line?"; constraint-eliminates-an-option test; genuinely-different-options test; the is-this-one-decision test (#37's trigger); the research recognition test on borderline asks. This is a rubric judge: distill GUIDE §Neutralizing-bias + §pre-flight into a scored rubric, one cheap call, threshold — standard 2026 practice, with known failure modes to design against (position/verbosity/self-preference bias; rubric drift) ([DeepEval judge guide](https://deepeval.com/blog/llm-as-a-judge), [PReMISE — rubrics as measurement specs, arXiv 2605.30803](https://arxiv.org/pdf/2605.30803), [RubricHub coarse-to-fine rubric generation, arXiv 2601.08430](https://arxiv.org/pdf/2601.08430)).

Two contested design points, both held open:
- **Gate posture:** hard gate (non-conformant brief refuses to run — protects every debate dollar, but a false positive blocks a legitimate commission and Lane A has no appeal channel) vs advisory (score + warnings attached, run proceeds — never blocks, but #53-class incidents keep billing). A middle path exists (hard on linter, advisory on judge), which is itself a third option.
- **One craft, two artifacts:** the GUIDE stays the human-canonical prose; the schema+rubric are executable *derivations* of it. That reintroduces the exact ESSENTIALS↔PLAYBOOK drift risk CLAUDE.md §5.6 warns about. Options: (a) hand-derive and version the pair, reconciling on GUIDE edits (cheap, drifts); (b) make the rubric the canonical artifact and *generate* the human prose from it (inverts authority — a real governance change); (c) optimize the template/rubric offline against accumulated outcomes, GEPA-style reflective evolution on traces ([DSPy GEPA](https://dspy.ai/getting-started/gepa-optimization/), [gepa-ai](https://github.com/gepa-ai/gepa)) — the only option that makes the template *improve* from usage rather than merely persist; also the most machinery.

## 4. Managing the boost — the honesty loop

The boost is itself an LLM output and can hallucinate a question the caller never meant; a system whose premise is "the caller words it badly" has no license to assume the boost words it *rightly*. Field practice converges on three controls, all applicable here:

1. **Approval of the actual payload, before billing.** HITL practice is explicit: approve the concrete artifact, not a summary of it, at the last point before cost/side-effects ([approval-path design](https://digitalthoughtdisruption.com/2026/07/12/human-in-the-loop-ai-agent-approval-paths/); pre-execution intervention is the cheap point to fix misalignment — [Magentic-UI, arXiv 2507.22358](https://arxiv.org/pdf/2507.22358)). Mechanism options (≥2 live): **(a) two-phase commit** — boosting is a separate invocation that *returns* the boosted brief as a file; nothing debates until the caller re-submits it (works identically for agents and humans; Lane A stays stateless; the repo already has the two-phase precedent in `_interactive_confirm_mode`'s detect-then-confirm shape, `cli.py:836`). **(b) inline with explicit consent** — `council --raw "..."` prints the boosted brief + a diff-against-raw and requires confirm interactively or a `--accept-boost` flag headless. For Lane B, (a) becomes a **two-pass tray**: the inbox emits `*-boosted.md` back into the tray for the operator's next pass instead of running immediately — noting the inbox-mirror blind spot (CLAUDE.md §10) means whichever mechanic ships must ship on both paths at once.
2. **Provenance inside the artifact.** Every boosted brief carries a provenance block: raw ask verbatim, boost template version, per-line `given/restructured/assumed` tags, unfilled holes, gate score. The `assumed` list doubles as the clarify-question list (Design B for free, deferred to the caller's discretion). Field basis: audit trails pairing original+rewritten queries are the established query-rewriting trust mechanism ([Sandgarden](https://www.sandgarden.com/learn/query-rewriting), [ZenML — rewrites as versioned artifacts](https://www.zenml.io/blog/query-rewriting-evaluation)). Where it lives: frontmatter of the brief (travels with the artifact; immutable once archived per §5 rule 3) vs a sidecar ledger (keeps briefs clean; joins the #82 ledger-fragmentation problem) — both live.
3. **Feedback loop with a free supervision signal.** Log per commission: raw ask → boosted brief → caller's *edits* to it → gate score → mode routed → debate outcome. The edit-distance between boosted and approved brief is ground-truth supervision on boost quality that costs nothing to collect; declining edit-distance over time is the boost's health metric, rising is its alarm. Template versions get the same treatment as code — request logs tied to prompt version, diffs reviewable before promotion ([Confident AI prompt-management survey](https://www.confident-ai.com/knowledge-base/best-ai-prompt-management-tools-with-llm-observability-2026), [LaunchDarkly LLM observability](https://launchdarkly.com/blog/llm-observability/)). This is also the corpus GEPA-style template evolution (§3c) would train on.

The prior audit's B4 ("no adoption evidence ever returns") reappears here at smaller scale and is fixable at this scale: the input layer can close *its* loop (was the boosted question the one the caller meant?) even while the outer loop (was the verdict acted on?) stays open.

## 5. The ADR-11 tension

ADR-11 rejected a library API and MCP; the advisor therefore lives as "prompts the caller's agent improvises with." Does a real boosting layer force reopening it? **The answer depends on which mechanism from §1 is chosen — the mechanism decides the governance question, not vice versa:**

- **Designs A and C do not force it.** Both are expressible as stateless file-in/file-out CLI (`council boost`) or as pure caller-side prompt packs. A council-side `boost` subcommand *extends* the committed surface (contract bump to 1.1/2.0, an ADR) but stays inside CLI-as-ABI — ADR-11's actual rejection (stateful library/server surfaces) is untouched. Even Design B survives as a two-phase *file* protocol (boost returns `questions.md`; answers come back as a file) — clunky but contract-pure.
- **Design B done properly is the one true reopener.** MCP's elicitation primitive (added in the 2025-06-18 spec, maturing through the [2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)) is *exactly* the missing ask-back channel: a server mid-tool-call requests schema-validated structured input from the caller ([spec](https://modelcontextprotocol.io/specification/draft/client/elicitation), [The New Stack how-to](https://thenewstack.io/how-to-implement-elicitation-with-model-context-protocol/)). A thin MCP adapter shelling to the same CLI (prior audit M4-b) would make the clarify-loop first-class for every MCP-speaking caller. Cost: the adapter (S–M) + amending ADR-11's considered-and-rejected section + a second surface to keep honest.

Two positions, both live, with the costs attached:
- **Hold ADR-11; ship caller-side (#36 as published template+prompts, plus the linter as a script callers may run).** Cost S. Honest weakness: the Council's claim to *own* the craft becomes "the Council publishes the craft" — every caller agent executes it differently, there is no shared telemetry (§4.3's loop never accumulates), and quality depends on the caller's model. This is the status-quo trajectory of #36/#37/#38 as written.
- **Amend/extend: council-side entry stage under CLI-as-ABI (A or C as `council boost`), MCP adapter deferred as a separately-decidable rider.** Cost M + one contract ADR. Weakness: moves substance-shaping council-side (ADR-95 needs its boundary rule written down), and the entry stage becomes billable surface the Council must maintain and version forever.

The lane-split compromise (council-side boost for Lane B, published advisor for Lane A) remains live from §1 — it matches the OpenAI product/API precedent exactly, at the price of two divergent input experiences, which the inbox-mirror lesson says this repo historically handles badly.

## 6. One big swing — for the input layer specifically

Two candidates, deliberately unconverged (they answer different questions: *who authors* vs *what the artifact is*):

**Swing I — invert authorship: the Council interviews; the caller witnesses.**
Stop treating the brief as the caller's homework that the Council grades, and make brief-*production* the Council's first service: raw ask in → intake pipeline (classify → self-serve context pull from what the caller attached → ≤3 clarifying questions → draft → gate) → the brief comes back *to* the caller for approval as §4's two-phase commit → only then does anything debate. #36, #37, #9, and #53 collapse into one built stage; the GUIDE becomes that stage's spec instead of unread documentation; "the Council knows question-craft better than the caller" becomes an operating fact instead of a belief.
*Trades:* the ADR-95 lane boundary is redrawn openly (the Council becomes co-author of its own inputs — the provenance block is what keeps that honest); Lane A needs the two-phase file protocol or the MCP rider; intake becomes a real cost/latency stage on every commission; and a Council that authors its own questions can bias them — the gate must therefore run on the Council's *own* boosts with the same severity as on human briefs, and the §4 edit-distance loop is the standing check that intake serves callers rather than itself.

**Swing II — the brief is compiled, not written: BRIEF-SCHEMA v1 as the real contract input.**
Define a small machine schema — decision-sentence, options[] with tradeoff, facts[] each with provenance, constraints[] each naming what it eliminates, deliverable enum, prior-ADR refs — as the actual input contract; the markdown GUIDE format becomes a *rendering* of a schema instance. Boosting = compiling a raw ask into a schema instance **with typed holes**; holes *are* the clarifying questions; the linter is schema validation; #9's judge scores fields, not prose; decomposition = one ask compiling to N instances. This is the spec-driven-development bet applied to questions ([Spec Kit](https://github.github.com/spec-kit/), [Fowler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)): the spec is the primary artifact and everything downstream is generated. It makes the input layer testable, diffable, versionable like code — and gives every design in §1–§5 a stable target instead of 599 lines of prose.
*Trades:* schema rigidity vs question expressiveness (the GUIDE's own escape hatch — "if the most important point doesn't fit a heading, include it anyway" — must survive as an explicit overflow field or the schema silently narrows what can be asked); a second canonical form of the question craft (§3's drift problem, now load-bearing); and real briefs authored by humans in markdown need a lossless parse path in, or the schema becomes agent-only.

The two swings compose (I is *who runs* the pipeline, II is *what it emits*) — but each is independently adoptable, and adopting II first makes I cheaper later, while adopting I first makes II's schema discoverable from real intake transcripts. That ordering choice is the operator's.
